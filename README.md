## Database schema overview

9 models, matching the spec's table list:

| Model | Purpose |
|---|---|
| `Admin` | Single admin login (bcrypt password hash) |
| `CompanySettings` | Single-row config: company name/address, NOWD/NOPH/NOPL constants, ESI/PF rates |
| `Department` | Employee departments |
| `Employee` | Full profile: basic info, bank/statutory details, salary structure, leave balances |
| `AttendanceStatus` | Lookup table driving the leave rules engine (Present, Half Day, LOP, etc. with `payFraction`) |
| `Attendance` | One row per employee per date, unique constraint on `(employeeId, date)` |
| `LeaveTypes` | CL/SL/EL/PL/Maternity/Paternity policy reference |
| `Payroll` | One row per employee per month, unique constraint on `(employeeId, month, year)`, stores every earnings/deduction line |
| `SalarySlip` | 1:1 with a `Payroll` record, stores the generated PDF path |

**Design notes:**
- `AttendanceStatus.payFraction` (1.0 / 0.5 / 0.0) is what makes the leave rules engine (Step 4) data-driven instead of hardcoded — Present/Holiday/Weekly Off/CL/SL/etc. = 1.0, Half Day = 0.5, Loss Of Pay = 0.0.
- `Payroll` stores prorated earnings (`basicEarned`, `hraEarned`, etc.) separately from the employee's base `Employee.basic/hra/...` ("scale") — this mirrors the uploaded salary slip format (SCALE column vs EARNINGS column).
- All money fields use `Decimal` (not `Float`) to avoid floating-point rounding errors in payroll — standard practice for financial data.

## Step 2 — Auth

**Backend endpoints** (`/api/auth`):

| Method | Path | Auth required | Purpose |
|---|---|---|---|
| POST | `/login` | No | `{ username, password }` → `{ token, admin }` |
| POST | `/logout` | Yes | Client discards the token; endpoint exists for symmetry |
| GET | `/me` | Yes | Returns the current admin — used on page load to validate a stored token |
| POST | `/change-password` | Yes | `{ currentPassword, newPassword }` — requires current password to confirm identity |

**How it works:**
- Passwords are hashed with bcrypt (10 salt rounds), never stored or returned in plaintext.
- `requireAuth` middleware checks `Authorization: Bearer <token>`, verifies it, and attaches `req.admin = { adminId, username }`.
- There's deliberately no registration endpoint — the one admin account is created only by `prisma:seed`. To reset credentials, re-run the seed on a fresh DB or update the row directly.
- Login and password-mismatch errors return the same generic message ("Invalid username or password") so a caller can't tell whether the username exists.

**Frontend:**
- `AuthContext` holds the logged-in admin in memory and the JWT in `localStorage` (`hrms_token`).
- On app load, if a token exists, it's validated against `/auth/me` rather than trusted blindly — an expired/tampered token gets cleared automatically.
- `services/api.ts` is an axios instance that attaches the token to every request and auto-redirects to `/login` on any `401` response (e.g. token expired mid-session).
- `ProtectedRoute` wraps any page that requires login; `/login` is the only public route.
- `/dashboard` is currently a placeholder proving the full loop (login → protected page → change password → logout) works — Steps 3–8 replace it with the real app shell (sidebar + pages).

**Test it once the backend is running:**
```bash
curl -X POST http://localhost:5000/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"admin","password":"admin123"}'
```

## Step 3 — Employee + Department CRUD

**Backend endpoints:**

| Method | Path | Purpose |
|---|---|---|
| GET | `/api/departments` | List all, with live employee counts |
| POST | `/api/departments` | Create (name must be unique) |
| PUT | `/api/departments/:id` | Rename |
| DELETE | `/api/departments/:id` | Blocked with a clear error if employees are still assigned |
| GET | `/api/employees` | List with `search`, `departmentId`, `status`, `page`, `pageSize`, `sortBy`, `sortDir` query params |
| GET | `/api/employees/:code` | Full detail for one employee |
| POST | `/api/employees` | Create — `code` is server-generated (EMP001, EMP002…), never accepted from the client |
| PUT | `/api/employees/:code` | Partial update (only send changed fields) |
| DELETE | `/api/employees/:code` | Delete — cascades to their Attendance/Payroll/SalarySlip rows per the schema |

All routes require the `Authorization: Bearer <token>` header from Step 2.

**Employee code generation:** `generateNextEmployeeCode()` reads the highest existing numeric suffix (not a separate counter table) so it self-heals if a record is ever deleted — no gaps become a bug, and it never depends on in-memory state that would break across server restarts.

**Validation:** every write goes through a Zod schema before touching the database — required fields, enum values (gender, employment type, payment mode), and number lower-bounds are all enforced server-side, not just in the React form.

**Frontend:**
- `/employees` — full table with search (name/code/mobile/designation), department filter, status filter, sortable columns, pagination (20/page), and a modal form covering Basic Info, Bank & Statutory Details, and Salary Details — matching the three sections from the spec.
- `/departments` — list with live employee counts, add, and delete (delete is blocked client-side with the same message the API returns if employees are still assigned).
- `components/Layout.tsx` is the shared authenticated shell (sidebar + topbar) that Steps 4–8 will keep extending with new nav items — Attendance, Payroll, Reports, Settings.
- Net salary shown in the employee table is a quick client-side estimate (gross allowances minus fixed deductions); the real prorated figure comes from the Payroll engine in Step 5.

## Step 4 — Attendance module + leave rules engine

**Backend endpoints** (`/api/attendance`, all behind `requireAuth`):

| Method | Path | Purpose |
|---|---|---|
| GET | `/statuses` | Lookup list of all attendance statuses (for the marking dropdown) |
| GET | `/leave-types` | Lookup list of CL/SL/EL/PL/etc. policy definitions |
| GET | `/?date=YYYY-MM-DD` | Every active employee + their status for that date (`null` if unmarked) |
| POST | `/` | Bulk save: `{ date, entries: [{ employeeId, attendanceStatusCode, remarks? }] }` |
| GET | `/report?year=2026&month=6` | Monthly grid (every employee × every marked date) + payable-days summary |

**The leave rules engine** (`services/leaveRules.service.ts`) is the key piece: rather than hardcoding "CL = paid, LOP = unpaid" in an if/else chain, it reads each day's `AttendanceStatus.payFraction` (1.0 / 0.5 / 0.0, seeded in Step 1) and sums it up per employee per month. `computeAttendanceSummaryForAll` does this in one query for every employee, so the monthly report — and the Step 5 payroll engine — never do N+1 lookups.

**Why bulk upsert instead of per-employee saves:** the schema's `@@unique([employeeId, date])` constraint means POSTing the same date twice always updates existing rows instead of duplicating them — this is what makes "attendance can be edited later" (from the spec) just work, with no separate edit endpoint needed.

**Frontend:** `/attendance` page has two parts — a daily marking grid (date picker, per-employee status dropdown defaulting to Present, "Mark All Present" shortcut, single Save button) and a monthly report below it (date × employee grid with payable-days and LOP totals per employee, driven by the same leave rules engine).

## Step 5 — Payroll calculation engine

**Schema addition:** `PayrollAdjustment` — a small table for the handful of per-month inputs that can't be derived from Attendance (OT hours, an LOP override, salary advance, tax, one-off allowance). Unique on `(employeeId, month, year)`.

**Backend endpoints** (`/api/payroll`, all behind `requireAuth`):

| Method | Path | Purpose |
|---|---|---|
| GET | `/adjustments?year=&month=` | Every active employee's adjustment row (defaults to zero/null if unset) |
| POST | `/adjustments` | Bulk upsert adjustments for a month |
| POST | `/generate` | `{ year, month }` → runs the engine for every active employee, upserts `Payroll` rows |
| GET | `/:employeeCode?year=&month=` | One employee's payroll record (used by the Step 6 slip) |
| GET | `/?year=&month=` | Full payroll table for a month + total net salary paid |

**The engine** (`services/payrollEngine.service.ts`) is the server-side version of the prototype we built earlier, now DB-backed and reusing the Step 4 leave rules engine instead of re-deriving LOP itself:

1. Reads `CompanySettings` for NOWD/NOPH/NOPL and the ESI rate.
2. Calls `computeAttendanceSummary` (Step 4) to get attendance-derived LOP days — unless a `PayrollAdjustment.lopOverride` exists for that employee/month, in which case that wins.
3. Prorates Basic/HRA/DA/Special/Medical/Conveyance/Washing by `daysWorking / NOWD` — matching how the Visalam slip shows reduced earnings under the SCALE vs EARNINGS columns.
4. Adds OT (hours × employee's rate) and any one-off allowance.
5. Deducts ESI (% of earnings, only if `esiApplicable`), canteen (rate × days worked), PF, professional tax + any manual tax, rent, advance, and other fixed deductions.
6. Everything is stored back on the `Payroll` row — nothing is left implicit or recalculated on the fly at slip-generation time, so a slip printed today matches one printed a year from now even if the employee's current salary changes later.

**Regeneration is safe:** `Payroll` has `@@unique([employeeId, month, year])`, so `generatePayrollForMonth` always upserts — regenerating after fixing an attendance mistake overwrites the existing row rather than creating a duplicate, per the spec's "Admin can regenerate payroll after attendance changes."

**Frontend `/payroll` page:** month picker, Generate/Regenerate button, an "Edit OT / LOP / Advance" button opening `AdjustmentsModal` (per-employee inputs, save then regenerate to apply), and the resulting payroll table with a total-net-salary footer row. Each row links to `/payroll/slip/:code/:year/:month` — the real PDF viewer, built in Step 6.

## Step 6 — Salary slip PDF generator

**Backend:**
- `services/salarySlip.service.ts` — draws the slip with PDFKit, matching the uploaded Visalam Industries layout line-for-line: company header, employee name, the `<Month>-<Year>-NOWD X  LOP Y  OT HOURS Z` line, `No of days working X  NOPH Y  NOPL Z` line, `EMP.CODE / MODE / ESI NO` line, the SCALE | EARNINGS | DEDUCTIONS grid with a Leave Avl (EL/CL) column, a shaded TOTAL row with NET PAY, amount-in-words, and a signature line. Page size is A5 to match a typical payslip printout.
- `buildSlipData()` is kept separate from the drawing code — it just shapes a `Payroll` + `Employee` + `CompanySettings` row into the fields the PDF needs — so Step 7's reports can reuse the same data shape without re-deriving it.
- `utils/amountInWords.ts` — converts the net salary into Indian-numbering-system words (Crore/Lakh/Thousand), same logic as the HTML prototype, now on the server.
- **The PDF is generated from the stored `Payroll` row, not recalculated from the employee's current salary** — so a slip for March still shows March's numbers even if the employee's pay changes in April. Each generation is also persisted to `uploads/salary-slips/` and recorded in the `SalarySlip` table (`pdfPath`, `amountInWords`), so Step 7 can list/link to previously generated slips without regenerating them.

**Endpoint:** `GET /api/payroll/:employeeCode/slip?year=&month=` — returns the PDF directly (`Content-Type: application/pdf`), behind `requireAuth` like everything else.

**Frontend:** `/payroll/slip/:code/:year/:month` now fetches the PDF as an authenticated blob (a plain `<a href>` can't carry the JWT header), displays it inline in an iframe, and offers Download and Print buttons — Print opens the PDF in a new tab and triggers the browser's native print dialog once it's loaded.

## Step 7 — Reports + Excel/PDF export

**Backend endpoints** (`/api/reports`, all behind `requireAuth`, all support `?format=json|xlsx|pdf`):

| Path | Report | Needs year/month? |
|---|---|---|
| `/employees` | Employee Report — code, name, department, designation, status, mobile, joining date | No |
| `/departments` | Department Report — name + live employee count | No |
| `/attendance` | Attendance Report — present/half-day/LOP/payable days per employee | Yes |
| `/payroll` | Payroll Report — the actual generated payroll rows for a month | Yes |
| `/salary` | Salary Report — each employee's *current configured* salary structure (not tied to a specific month — useful for audits) | No |
| `/leave` | Leave Report — CL/SL/PL usage this month + EL/CL balances | Yes |

**Design:** every report shares one response shape (`{ title, columns, rows }`) and one export path. `services/reportExport.service.ts` has exactly two functions — `exportToExcel` and `exportToPdfTable` — that any report controller can call with its columns/rows; adding a 7th report later means writing a query, not a new export pipeline. Excel exports use ExcelJS with a styled header row and autofilter; PDF exports use PDFKit with automatic pagination for long reports (e.g. payroll for 100 employees spans multiple landscape A4 pages cleanly).

**Frontend `/reports` page:** tabs across the six report types, a month picker that only appears for the three reports that need it, and Export Excel / Export PDF / Print buttons. Numeric currency-like columns (salary, earnings, deductions) are auto-formatted with ₹ and Indian digit grouping on screen; the raw numbers go into the Excel export instead, so the spreadsheet stays numeric/sortable rather than string-formatted.

## Post-launch additions

Three features added after the initial 8-step build, at the user's request:

### 1. Multi-user roles (Manager / Accountant / HR Staff)

The single `Admin` model was replaced with a `User` model that has a `role` (`MANAGER` / `ACCOUNTANT` / `HR_STAFF`) and an `isActive` flag.

- **MANAGER** is the primary role — created once by the seed script, exactly like the old single admin. Only a Manager can create Accountant/HR Staff accounts, activate/deactivate them, reset their passwords, or delete them (`/api/auth/users/*`, all behind `requireRole('MANAGER')`). A Manager account can't be deactivated or deleted through the API — there's always at least one way in.
- **ACCOUNTANT** gets access to Payroll and Reports.
- **HR_STAFF** gets access to Employees, Departments, and Attendance.
- Every route that changes data (not just reads it) now has a `requireRole(...)` check matching this split — see the updated route files for the exact breakdown. Dashboard and Reports stay readable by any logged-in role.
- `requireAuth` now re-checks `user.isActive` on every request (not just at login), so deactivating someone mid-session locks them out on their very next API call rather than only at their next login.
- **Frontend:** the sidebar (`Layout.tsx`) filters nav items by the logged-in user's role, a new `/users` page (Manager-only) handles account creation/management, and a role badge shows next to the username in the topbar.

### 2. Employee photo + company logo upload

- New `config/uploads.ts` sets up Multer disk storage for two upload types: employee photos (`uploads/employee-photos/`) and the company logo (`uploads/company/`), both restricted to JPEG/PNG/WEBP, 5MB max.
- `POST /api/employees/:code/photo` and `POST /api/settings/logo` save the file and record its URL on the `Employee.photoUrl` / `CompanySettings.logoUrl` field respectively.
- Uploaded files are served statically at `/uploads/*` (added to `app.ts`; note `helmet`'s `crossOriginResourcePolicy` had to be disabled, since the frontend on port 5173 loads these images directly from the backend on port 5000).
- **The logo genuinely reflects everywhere from one upload:** the sidebar (`Layout.tsx`, via a small shared `useCompanyBranding` hook with an in-memory cache) and the salary slip PDF (`salarySlip.service.ts` now resolves `CompanySettings.logoUrl` to a filesystem path and draws it with `doc.image()` in the header) both read from the same `CompanySettings` row. Company name is edited on the same Settings page and already flowed everywhere via that row — no separate wiring needed.
- Employee photos show as a clickable circular thumbnail in the Employees table — clicking it opens a file picker and uploads immediately, no separate modal needed.

### 3. Stricter field validation (PAN / Aadhaar / IFSC / Mobile)

Previously these fields accepted any text. Now both the manual Employee form (`employee.controller.ts`) and bulk import (`employeeBulkImport.controller.ts`) enforce:

- **PAN:** `ABCDE1234F` format (5 letters, 4 digits, 1 letter) — auto-uppercased before validating, so lowercase input isn't wrongly rejected
- **Aadhaar:** exactly 12 digits
- **IFSC:** 11 characters, e.g. `CNRB0001234` — also auto-uppercased
- **Mobile:** 10-digit Indian number starting with 6-9

All four are still *optional* fields — an empty value always passes — but a non-empty value that doesn't match the real format is rejected with a specific message (e.g. "PAN must be in the format ABCDE1234F"), both inline in the Employee form and per-row during bulk import (a bad PAN in row 12 doesn't stop rows 1-11 and 13+ from importing). The frontend form also shows format placeholders (e.g. "CNRB0001234") so people see the expected shape before they even submit.

### 4. Bulk employee import (Excel)

- `GET /api/employees/bulk-import/template` generates a `.xlsx` on the fly (ExcelJS) with the exact columns the importer expects, one italicized example row, and a "Read Me" sheet listing valid departments, date format, and employment-type values — so HR fills in a file that's guaranteed to match what the parser expects.
- `POST /api/employees/bulk-import` parses the uploaded file row by row. **A bad row never aborts the batch** — every valid row is still created, and every invalid row is reported back with its row number, employee name, and the specific reason (unknown department, non-numeric salary, missing name, etc.), so HR can fix just those rows and re-upload if needed rather than starting over.
- Employee codes are still auto-generated per row via the existing `generateNextEmployeeCode()` — bulk import doesn't bypass that.
- **Frontend:** `BulkImportModal.tsx`, opened from a new "Bulk Import" button on the Employees page, walks through both steps (download template → upload filled file) and shows the created count plus a per-row error table. After a successful import, the user is pointed back to the Employees list to open each new employee and add a photo if needed — bulk import doesn't attempt to also handle photos, since spreadsheets can't carry image files per row in a way worth the complexity here.

### 5. Audit trail

A new `AuditLog` table records who changed what, when — every create, update, delete, and login attempt across the system.

**Why this isn't one generic middleware:** Express has no built-in way to know what a request is about to change before it hits the database — a generic "log every request" middleware can record *that* something happened, but not *what* changed (the old value vs. the new one), since it never sees the row before the controller reads it. So instead, `services/audit.service.ts` exports two small helpers:

- **`logAudit(...)`** — writes one entry: who (from `req.user`, or an explicit override for pre-auth events like login), what action (`CREATE`/`UPDATE`/`DELETE`/`LOGIN`/`LOGIN_FAILED`), which entity and ID, a human-readable description, and an optional field-level `changes` object. It never throws — a logging failure can't block the actual operation it's describing.
- **`diffFields(before, after, ignoreKeys)`** — compares two objects and returns only the fields that actually changed, in `{ field: { before, after } }` shape, so an update to one salary field doesn't bury the log in 30 unchanged columns.

**Every mutating controller calls this explicitly** at its point of change — that's the "touches every controller" tradeoff mentioned when this was scoped, but it's what makes the log actually useful instead of just a request tape recorder:

- **Employee** — create, update (with field diff), delete, photo upload
- **Department** — create, rename (with before/after name), delete
- **Attendance** — one summary entry per day's save (not per employee, to avoid flooding the log with routine daily marking)
- **Payroll** — generation runs, adjustment saves (OT/advance/tax/LOP overrides)
- **CompanySettings** — field updates (with diff), logo uploads
- **User accounts** — created, activated/deactivated, password reset, deleted
- **Auth** — every login attempt is logged, including **failed ones** (unknown username, wrong password, deactivated account) — this is the one place logging happens *before* `req.user` exists, which is why `logAudit` accepts `actorUserId`/`actorUsername` overrides

**Access:** `GET /api/audit-logs` is MANAGER-only (`requireRole('MANAGER')`), filterable by entity type, action, username, and date range, paginated at 30/page. The frontend `/audit-log` page (also MANAGER-only in the sidebar) shows a live table with those filters; clicking a row with a field-level diff expands it into a before/after mini-table inline.

### 6. Leave request workflow (no employee login)

The spec calls for "no employee login," so this is built as **option (a)**: a lightweight, no-login public form reachable only via a unique per-employee link, rather than giving employees real accounts.

**How the link works:**
- `Employee.leaveRequestToken` is a random 32-character token, `null` until generated.
- A Manager or HR Staff user clicks **"Copy Leave Link"** on the Employees page → `POST /api/employees/:code/leave-link` generates (or **regenerates**, invalidating any previously shared link) the token and copies the full URL (`/leave-request/EMP004/<token>`) to the clipboard, ready to paste into WhatsApp, email, whatever channel is used to reach that employee.
- That URL is the *only* credential — there's no username/password for employees. `publicLeaveRequest.routes.ts` is mounted with **no `requireAuth`** at all; the token in the URL path is the entire access control.

**What the employee sees at that link** (`PublicLeaveRequestPage.tsx`, styled deliberately outside the app's dark-mode/sidebar shell since it's a standalone page): their name (confirms the link is theirs), a form (date range, leave type, reason), and their own last 10 requests with status — so they can check on a pending request without asking anyone.

**Review workflow:** submissions land as `PENDING` in `LeaveRequest`. The `/leave-requests` page (Manager/HR Staff) lists them with Approve/Reject actions and an optional note. **Approving a request doesn't just change a status flag** — it writes/overwrites an `Attendance` row for every date in the range using the requested leave type, going through the exact same `AttendanceStatus`/leave-rules-engine path a manually marked day would. That means an approved leave request flows straight into the next payroll run automatically — no separate step to "remember" to mark those days present/absent.

Rejecting a request only records the decision; no attendance is touched, so a rejected request never accidentally affects pay.

### 7. Backup / restore tooling

Two scripts in `backend/scripts/`, run via `npm run backup` and `npm run restore`:

- **`backup.ts`** parses `DATABASE_URL` from `.env`, shells out to `mysqldump` (password passed via the `MYSQL_PWD` environment variable, never a CLI flag, so it never shows up in process listings or shell history), and writes a timestamped `.sql` file to `backend/backups/`. It then **prunes old backups automatically**, keeping only the most recent `BACKUP_RETENTION_COUNT` (default 14) so an automated daily schedule doesn't grow the folder forever.
- **`restore.ts`** takes a filename (or full path) as an argument, shows exactly what it's about to overwrite, and **requires typing "yes"** before doing anything — there's no `--force` flag or way to skip that confirmation, since this is a destructive, whole-database operation.

```bash
cd backend
npm run backup                              # creates backend/backups/hrms_payroll-2026-07-10T....sql
npm run restore                             # no argument: lists available backups
npm run restore -- hrms_payroll-2026-07-10T....sql
```

**Scheduling on Windows** (since this runs on your laptop): Task Scheduler → Create Basic Task → Trigger: Daily → Action: **Start a program** → point it at `backend\scripts\run-backup.bat` (a small wrapper included so Task Scheduler has a simple double-clickable target with the working directory set correctly) → set it to run whether you're logged in or not if you want it to work even when the laptop is locked.

**This requires `mysqldump` and `mysql` to be on your PATH** — the same PATH entry you already set up during MySQL installation covers both, since they live in the same `bin` folder.

### 8. Configurable permissions (replaces hardcoded roles)

This is a real architecture change, not a bolt-on: **every `requireRole(...)` check across every route file was replaced** with a database-driven `requirePermission('key')` check. The three roles (Manager/Accountant/HR Staff) still exist, but *what each role can do* is now data, not code.

**New schema:**
- `Permission` — the full catalog of ~28 fine-grained actions (`employees.create`, `payroll.generate`, `settings.manage`, etc.), grouped into categories for the admin UI. Defined once in `prisma/permissions.seed.ts`.
- `RolePermission` — the default allow/deny for each (role, permission) pair. Seeded to match exactly what was previously hardcoded, so migrating to this system is behavior-neutral until someone actually changes something.
- `UserPermissionOverride` — an explicit grant or revoke for one specific person, which always wins over their role's default. This is what makes it "role **or** person" configurable, not just role-configurable.

**Resolution logic** (`services/permission.service.ts`, `hasPermission()`): check for a personal override first; if none exists, fall back to the role default; if neither is configured, deny (fail-closed — an unrecognized permission key never silently allows access).

**Safety rail:** the Manager role can never lose `users.manage` or `permissions.manage`, and no individual Manager account can have either revoked via a personal override. Both the role matrix and the per-person override endpoints reject that specific change with a clear error — without this, it would be possible to configure every Manager account into a state where nobody can manage users or permissions anymore, with no way back in short of editing the database directly.

**Admin UI** (`/permissions`, gated by the `permissions.manage` permission itself):
- **Role Defaults tab** — a checkbox matrix, permissions (grouped by category) × the 3 roles. Toggling a cell saves immediately (optimistic UI, rolled back if the server rejects it — e.g. the safety rail above).
- **Per-Person Overrides tab** — pick any non-Manager user, see their full effective permission list, and for each one choose **Default** (use their role's setting), **Allow** (explicit grant regardless of role), or **Deny** (explicit revoke regardless of role).

**Frontend:** `AuthContext` now carries the logged-in user's `permissions: string[]` (returned by `/auth/login` and `/auth/me`), and exposes a `can(key)` helper. `Layout.tsx`'s sidebar filters every nav item by `can(item.permission)` instead of a hardcoded role array — so granting someone `reports.export` via the Permissions page, for example, makes Reports' export buttons usable without touching a single line of frontend code.

**One caveat, stated plainly:** a permission change takes effect for that person on their **next page load**, not instantly mid-session — the frontend doesn't poll for permission changes. If you revoke something from someone who's actively using the app, they'll still be able to use it until they refresh or the backend rejects their next request for that specific action (the backend check is always live; only the *frontend's knowledge* of what to show/hide lags until refresh).

### 9. Email / SMS notifications (payslip emailing, birthday reminders)

Two new dependencies: **Nodemailer** for email (works with any SMTP provider — Gmail, SendGrid, your own mail server) and **MSG91** for SMS (an India-focused gateway, matching the business's location). Both are **entirely opt-in** — the app runs completely normally with neither configured; notification-related buttons and toggles simply report "not configured" rather than erroring.

**Backend services:**
- `services/email.service.ts` — lazily builds an SMTP transporter from `SMTP_HOST`/`PORT`/`USER`/`PASS` in `.env`. If those aren't set, `sendEmail()` returns `{ success: false, error: 'SMTP is not configured' }` instead of throwing — every caller handles that gracefully rather than crashing.
- `services/sms.service.ts` — same pattern for MSG91 (`MSG91_AUTH_KEY`/`MSG91_SENDER_ID`). Uses MSG91's Flow API with a plain-text message; if your MSG91 account requires a DLT-registered template (mandatory for some transactional SMS categories in India), swap the request body for a template ID — see the comment in that file.
- `services/notification.service.ts` — the actual payslip and birthday logic:
  - `emailPayslipToEmployee()` — builds the same PDF as the Step 6 slip generator and emails it as an attachment. Checks the employee has an email on file and that `CompanySettings.emailNotificationsEnabled` is on before doing anything; either miss is logged as `SKIPPED`, not `FAILED`.
  - `emailAllPayslipsForMonth()` — loops every generated payroll record for a month, calling the function above per employee, and returns a `{ sent, skipped, failed, details }` summary rather than aborting on the first failure.
  - `sendTodaysBirthdayGreetings()` — checks every active employee's `dob` against today's month/day, sends via whichever channels are enabled.
- `services/notificationLog.service.ts` + the `NotificationLog` table — every attempt (sent, failed, or skipped) is recorded with the recipient, channel, category, and error message if any, viewable at `/notifications`.
- `services/cron.service.ts` — registers an hourly `node-cron` job that checks whether "now" matches the configured `birthdayReminderHour` and hasn't already run today, then calls `sendTodaysBirthdayGreetings()`. Runs hourly rather than using a once-a-day cron expression so that toggling the reminder hour in Settings takes effect without restarting the server.

**New permissions:** `notifications.send` (manually email a payslip, one or bulk) and `notifications.view` (see the send history) — these slot into the Section 8 permission system like everything else, so a Manager can grant payslip-emailing to HR Staff (not included by default) from the Permissions page without any code change.

**Settings page** gained a Notifications card: toggles for email/SMS/birthday-reminders, a reminder-hour picker, and a live "configured on the server?" indicator per channel (checked via `GET /api/notifications/config-status`) — so a Manager can tell at a glance whether flipping a toggle will actually do anything yet, before wondering why nothing sent.

**Payroll page** gained an "Email" action per row and an "Email All Payslips" bulk button (both gated by `notifications.send`), with a results breakdown after a bulk send.

### 10. Gradient color theme

The UI was visually flat (solid green everywhere). Rather than touching every one of the ~20 page files that use `bg-accent`/`text-accent`, the fix is two CSS rules in `frontend/src/index.css` placed *after* Tailwind's generated utilities in the cascade — they override `.bg-accent` with a diagonal teal gradient and add a `.text-gradient` utility, so every existing button, badge, and active nav link across the whole app picks up the gradient automatically with zero component changes. On top of that, a few targeted touches: a gradient page background + gradient title on the Login page, a gradient top accent bar on the sidebar and a gradient underline on the topbar in `Layout.tsx`, and a gradient hero banner + highlighted "Total Employees" stat card on the Dashboard.

## Getting started (once you have MySQL running)

```bash
# Backend
cd backend
cp .env.example .env         # then edit DATABASE_URL, JWT_SECRET
npm install
npx prisma migrate dev --name add_roles_and_uploads    # applies the full schema, including the User/role model
npm run prisma:seed                   # seeds the manager account, departments, attendance statuses
npm run dev                           # starts API on http://localhost:5000

# Frontend (separate terminal)
cd frontend
cp .env.example .env
npm install
npm run dev                           # starts on http://localhost:5173
```

Default login after seeding: **admin / admin123**, with the **Manager** role — change the password immediately, then use the Users page to create Accountant/HR Staff accounts for anyone else who needs access.

> **If you already ran `prisma migrate dev --name init` before the multi-user/upload features were added:** just run `npx prisma migrate dev --name add_roles_and_uploads` again — Prisma will detect the schema changes (the new `User` model replacing `Admin`, the new `PayrollAdjustment` table, etc.) and generate the additional migration on top of what's already applied.

> **If you already have the multi-user/upload migration applied and are adding the audit trail:** run `npx prisma migrate dev --name add_audit_log` — this only adds the new `AuditLog` table, nothing else changes.

> **Adding the leave request workflow on top of an already-migrated database:** run `npx prisma migrate dev --name add_leave_requests` — adds the `LeaveRequest` table and the `leaveRequestToken` column on `Employee`. No re-seed needed.

> **Adding configurable permissions on top of an already-migrated database:** run `npx prisma migrate dev --name add_permissions`, then `npm run prisma:seed` again — the seed is idempotent for permissions (it upserts the catalog and only *creates* role defaults that don't already exist, never overwriting a default you've since customized), so re-running it after this migration is safe and necessary to populate the new tables.

> **Adding email/SMS notifications on top of an already-migrated database:** run `npx prisma migrate dev --name add_notifications`, then `npm run prisma:seed` again to pick up the two new permission keys (`notifications.send`, `notifications.view`). Also run `npm install` in `backend/` first — this feature added `nodemailer` and `node-cron` as dependencies.

No MySQL server handy? Swap `provider = "mysql"` for `"sqlite"` in `schema.prisma` and set `DATABASE_URL="file:./dev.db"` in `.env` — everything else works unchanged for local development.
